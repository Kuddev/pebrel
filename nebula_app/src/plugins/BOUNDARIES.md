# 插件、产品修复与核心变更的边界

本文件是插件扩展范围与产品 PR 分工的权威说明。这里区分可插件化的产品方向和
已经落地的接口；当前实现范围见 [README](README.md)，实际 Runtime 方法由
[`boundary.rs`](boundary.rs) 单一声明。列入扩展范围不表示已有对应接口。

## 1. 三种交付路径

1. **修复产品已有行为：产品 PR。** 原有功能不符合既定合同、产生错误或性能回归，
   应在其责任模块修复。正常终端使用不以安装某个修复插件为前提。
2. **增加可选能力和体验：插件。** 插件通过公开扩展点提供新增行为、界面和资源；
   停用后宿主仍具备完整的基础使用路径。
3. **缺少公共扩展点：先基础设施 PR，再功能插件。** PR 建设有明确所有权、权限和
   生命周期的接口；插件承载具体功能。接口尚未实现，不构成将该类功能永久排除出插件的理由。

插件自身的 Bug 在其插件版本中修复并重新审核；宿主 API 的 Bug 回到产品 PR。
产品新增的必需能力、平台支持和基础协议实现同样走 PR，PR 不只用于修 Bug。

## 2. 外观类明确属于插件范围

主题、配色、字体样式、图标、背景、美化包、侧栏和菜单的外观布局、鼠标轨迹、光标
效果及 shader 后处理，均属于可插件化能力。外观改动幅度不是判断是否触及核心的依据。

视觉兼容以已选的 Shadertoy 风格 GLSL shader 和参数约定为起点，保留自有风格与可选扩展。
这不是保证所有第三方 shader 已兼容；当前插件命令尚未接入 shader 执行路径。
新增绘制、布局或资源接口走基础设施 PR，具体美化仍由插件提供。

外观错误也要按责任区分：宿主的缺字、错位、错误命中或缩放回归由产品 PR 修复；
美化包自身的配色或 shader 错误由该插件更新修复。

## 3. 逐类判定

| 范围 | 插件承载的可选扩展 | 产品 PR 承载的行为 |
| --- | --- | --- |
| 终端 | 通过已授权宿主能力提供辅助工具与工作流 | PTY、VT、终端网格、输入语义、选择复制、会话与连接生命周期 |
| 设置菜单 | 新设置页、分组、排版和外观 | 设置含义、校验、保存、迁移、权限与恢复入口 |
| 侧栏与文件树 | 新视图、分组、筛选、装饰、菜单和布局 | 漏文件、路径错误、访问授权、宿主文件操作的正确性 |
| Git 树 | 新展示、状态装饰、分组和工作流 | Git 数据与宿主操作语义错误、仓库和文件状态损坏 |
| Markdown | 额外语法、特殊块、图表、交互与呈现 | 已支持语法的兼容缺陷、宿主解析和资源访问错误 |
| 代码编辑 | 可选补全、诊断、格式化、重构、AI 辅助与装饰 | 输入法、光标、选区、文档版本、撤销、保存与基础编辑正确性 |
| AI 能力 | 新工具、集成、辅助界面和可复用流程 | 已有集成合同的缺陷、共享会话和状态机错误 |
| SSH 资源监控 | 采样策略、指标展示、历史图表、告警与监控面板 | SSH 认证、凭证、连接/通道生命周期和协议正确性 |
| 性能与内存 | 观测、建议、已授权的缓存与任务优化策略 | 内存泄漏、核心算法、分配器、线程与调度缺陷、产品性能回归 |

“兼容”“优化”“体验提升”只是需求名称，不自动决定交付路径。先核对是既有行为
失效，还是新的可选能力。禁止用插件掩盖产品 Bug，或通过插件直接改写核心内存与状态。

## 4. 终端体验的宿主所有权

- PTY/VT、终端状态、终端输入、基础选择复制、焦点和会话生命周期由宿主拥有。
  插件不取得核心对象、裸指针、全局输入拦截权或替换核心实现的入口。
- 插件可以通过经审查、已授权的能力请求宿主操作；请求操作不等于拥有会话。
  关闭窗格、提交输入、执行命令等操作需要独立的目标、授权及生命周期设计，
  不由通用 Runtime 转发接口隐式开放。
- 插件界面可以灵活组织自己的布局与局部交互。宿主负责全局快捷键冲突、焦点和
  主布局规则；外围视图重排不转移终端会话所有权。
- 插件界面卸载、失败或重新加载不得隐式销毁原有 TerminalView/PTY。取消订阅、
  清理任务和丢弃过期结果属于插件资源释放，不包含关闭用户终端。
- 普通终端启动、输入和绘制不等待插件执行。现有同步 CLI 执行器不进入 GUI 回调。
- 基础设置、权限管理和恢复入口由宿主保留；停用插件后应恢复可用的基础界面。

## 5. 扩展接口 PR 的准入要求

新增扩展点要同时明确：它接收的数据、返回结果、所有者、授权范围、触发时机、
失效与取消条件，以及插件停用后宿主如何继续工作。直接暴露内部可变对象不是扩展点。

宿主继续负责文件/Git 数据与持久化、Markdown 文档模型、编辑器版本和撤销等公共规则。
插件提交结构化请求或结果，不复制一套互相竞争的核心状态。
格式化和代码操作应通过带文档版本的编辑请求进入宿主事务，不直接改宿主缓冲区。
SSH 监控通过已授权的宿主采样能力获取数据，不取得私钥、密码或连接对象；监控任务
结束、失败或停用不关闭用户正在使用的 SSH 终端。新增采样能力仍需先补宿主接口。

安全授权与性能策略分开：

- 功能访问按能力和范围一次授权，扩大权限重新询问，用户可撤销。
- 正常性能开销由宿主观测提示，用户决定限制或停用；动画策略由插件决定。
- 权限不符、协议无效和包校验失败是安全/正确性边界，直接返回失败，
  不将未授权操作交给性能提示流程。
- 现有 Lua 执行硬限额与未来用户可调资源策略的衔接尚未确定；本次边界修改不调整其数值。

## 6. 分发与不可信代码

正式市场的新插件和更新版本均经自动检查与人工审核。审核绑定具体版本与产物，
清单声明不是用户授权，市场审核也不授予文件、网络或终端访问权。

用户已选择 Wasm/Extism、宿主原生 UI 扩展、GLSL 视觉扩展与 TUF 可信分发的方向。
这些系统尚未集成，本文件不将方向描述成已经实现的隔离或防投毒保证。
更换执行引擎也不扩大宿主能力范围；网络、依赖、凭证和编辑操作仍需独立的宿主边界。

## 7. 当前命令地基的实际边界

`plugin check/run` 目前仅通过明确审查的 `runtime.describe` 查询接入 Runtime。
不自动开放 Runtime 的其他方法；其新增方法、别名和插件自写 `permissions` 均不构成授权。
原生命令与 Lua 请求在执行时都经过同一宿主方法检查。校验失败发生在 Runtime 传输前。

`runtime.describe` 返回的是 Runtime 服务说明，其 capability 列表不是插件权限列表。
`plugin check` 的 `host_runtime_methods` 才是当前命令入口公开的 Runtime 方法集合。
普通用户的 Runtime CLI 保留原有能力，不因插件边界收紧而缩减。

当前没有插件安装授权库、撤销管理、UI 插槽、shader 或 Wasm 宿主。敏感读取和控制
方法在相应授权接口落地前不开放。这是当前切片的实施边界，不是缩减上述插件产品范围。

## 8. 主项目与社区代码分工

- **主项目仓库**：宿主执行与授权边界、公共 API/SDK 契约、原生 UI/视觉接入，以及少量
  用于验证契约的插件示例。共享协议与宿主兼容性应在同一变更中验证。
- **独立社区插件仓库**：插件登记、来源、版本、审核记录及正式市场索引；社区共同维护
  的插件源码可以集中在 `packages/`，配套统一的检查和发布流程。集中源码不代表将插件
  编译进主程序，每个插件仍有独立身份、版本与审核产物。
- **其他作者的插件仓库**：作者可以独立维护具体功能、美化资源、源码和版本产物，
  通过社区目录登记；不强制每个插件单独建仓。插件自己的缺陷通过插件更新交付，
  宿主缺陷仍走主项目 PR。

插件发版不强制主程序发版；插件依赖不自动进入主项目的运行依赖。公共接口新增或
改变仍走主项目 PR，社区插件不反向获得修改核心的权限。当前仓库中的合同示例无需
为了分仓迁出。本次只确定分工，未创建远端社区仓库或发布市场。

检查不可信插件时，加载代码本身就是执行；测试 HOME/配置目录分离仅用于避免正常
试运行污染用户配置，不等于恶意代码隔离。执行检查的环境与发布凭证分离，正式市场
审核仍须绑定最终产物，而不是只检查入口函数形状。
