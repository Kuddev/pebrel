# Windows packages require embedded GPUI shaders

## Status

Cause reproduced with the distributed debug binary. The extracted release package
passes the same missing-source check. ZIP and installer entry points now reject
the debug configuration; local debug builds remain available.

## Context

A Windows portable package started on the build machine but failed on another
machine before opening a window. The panic reported a DirectWrite initialization
failure caused by a missing path. Checking executable freshness, architecture and
successful startup on the build machine did not establish portability.

## Evidence

- Pinned GPUI revision `7c662384cd77c1d1e1566206920e3a420ea6767b` selects
  `shader_resources::build_shader_blob` when `debug_assertions` is enabled.
- That branch canonicalizes `CARGO_MANIFEST_DIR/src/color_text_raster.hlsl` before
  initializing DirectWrite's emoji rasterization shaders. General rendering also
  reads `src/shaders.hlsl` from the same build-time source location.
- The release branch instead uses shader byte arrays generated by the dependency's
  build script and embedded in the executable.
- Redirecting only the test process's HLSL source reads to a nonexistent path
  reproduced the reported `DirectWriteTextSystem` / `os error 3` panic. No shared
  dependency files or permissions were changed for this check.

## Decision

Restrict `package-release.ps1` and `build-installer.ps1` to the release
configuration. Keep `build-windows-product.ps1 -Configuration debug` for local
development. Use the same fresh release binaries for both distribution formats.

## Rejected alternatives

- Distributing debug binaries because they open on the developer machine: the
  source checkout hides the external resource dependency.
- Recreating the build machine's absolute Cargo paths on recipient machines.
- Copying HLSL files beside the executable: the pinned debug loader does not
  resolve them relative to the executable.
- Patching the GPUI dependency merely to make local debug builds distributable:
  the existing release mode already embeds the required resources.

## Consequences

Distribution requires the release compiler/linker work and Windows SDK shader
compiler. Developer builds remain useful but cannot be packaged by these entry
points. Ordinary release startup still depends on supported Windows graphics APIs.

## Validation

The existing product-build script tests retain both release and debug build
coverage, and now verify that ZIP and installer entry points reject debug before
building or collecting files. The missing-source failure was reproduced in an
isolated debug process. Under the same process-local redirection, the extracted
release executable opened its native window, exposed the correct Runtime PID,
rendered Chinese text and color emoji, and shut down normally without reading
source HLSL. Its executable and bundled runtime hashes match the release build.
This is a targeted missing-resource check, not all-machine graphics certification.

## Supersedes

None.

## Revisit when

The pinned GPUI debug renderer gains a relocatable resource contract and that
contract is verified outside its source checkout.
