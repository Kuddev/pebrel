# Workspace shortcut source ownership

## Status

Proposed with the fix for #509. The filename uses the issue's public report date.
The stored `keybind=<combo>:<action>` format is unchanged.

## Context

GPUI owns one application-wide keymap. The workspace previously appended user bindings
and tracked each window's applied keys separately. Removing a preference appended
`Unbind(action)` and attempted to recreate the corresponding defaults. A global
`NoAction` generated by clearing a terminal shortcut could suppress an Input's paste
binding, and an `Unbind(NoAction)` could not undo that suppression.

## Evidence

The pinned GPUI keymap handles `NoAction` before consulting its list of unbound actions.
Its dispatch rules allow a null to suppress bindings from the same or weaker source.
Bindings without source metadata have priority zero. The command-dialog regressions
passed with fresh defaults and failed with persisted paste-removal rows, both before
and after clearing those rows in the same running workspace.

The config module intentionally omits platform defaults under `cfg(test)`. Reconstructing
the problem solely with `rebind_action` therefore misses the Windows removal records;
the regression uses the actual stored form and validates both real dialog inputs.

## Decision

`keyboard_bindings.rs` reserves source IDs 1 and 2 for user workspace overrides and
workspace defaults. Native component bindings remain untagged, at priority zero;
input-specific Paste aliases also remain untagged. A user null disables workspace
defaults while preserving the input's own editing action. An explicit workspace action
still follows GPUI's normal context and registration precedence.

An update snapshots the current keymap, drops only source 1, and appends the current
override records tagged with source 1. It then replaces the keymap in one UI-thread
update. This preserves other sources and component registrations added after startup.
The obsolete per-window registration history is removed.

## Rejected alternatives

- `Unbind(NoAction)` cannot remove the pinned keymap's control record.
- Reinitializing the component library to restore clipboard bindings repeats unrelated
  initialization and does not provide an ownership boundary.
- Restoring a few clipboard keys alone leaves stale nulls and unbounded update history.
- A window-local snapshot cannot reliably describe a shared application keymap.

## Consequences

Updating shortcuts clones the current binding list on a cold settings/window-creation
path. Its size stays bounded by other sources plus the current overrides, rather than
growing with each edit. No key-event hot path, persisted schema, protocol, or dependency
changes. Source identifiers are runtime metadata and must not be reused by other modules.

## Validation

`keyboard_bindings/tests.rs` covers actual dialog paste, clear/reset, explicit reassignment,
foreign registrations, repeated replacements, and updates from multiple windows. Dialog
paste tests use reduced motion so the entry animation cannot move Save between reading
its bounds and dispatching mouse events. Existing tab, rename and terminal-encoding
regressions remain applicable. The opt-in Windows
`native_paste_tests.rs` fixture uses the system clipboard and requires external verification
of the actual input values; it does not execute the pasted commands.

## Supersedes

None. The shared platform alias table remains authoritative.

## Revisit when

Another module needs keybinding source metadata, or the pinned GPUI changes source
priority/control-removal semantics. Add a shared source registry before allocating
overlapping identifiers. Do not replace the current keymap with a startup-only snapshot.
